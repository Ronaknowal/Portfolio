# Optical digits: data, fitted coordinates and execution provenance

Source: E. Alpaydin and C. Kaynak (1998), *Optical Recognition of Handwritten Digits*, UCI Machine Learning Repository, DOI [10.24432/C50P49](https://doi.org/10.24432/C50P49). The [UCI dataset page](https://archive.ics.uci.edu/dataset/80/optical+recognition+of+handwritten+digits) records the [Creative Commons Attribution 4.0 International license](https://creativecommons.org/licenses/by/4.0/). Dataset/source/license documentation was reviewed 12 September 2026. The original collectors do not endorse this lesson.

The collection was created to study handwritten digit recognition. Original preprocessing divides normalized bitmaps into 4×4 blocks and counts foreground pixels, producing 64 integers from 0 to 16 in an 8×8 array. A `pixel_i` value here is a block count, rather than an original camera pixel. This is the optical-digits collection, not MNIST. Scikit-learn's [dataset description](https://scikit-learn.org/stable/datasets/toy_dataset.html#optical-recognition-of-handwritten-digits-dataset) identifies its bundled 1,797 rows as the original test-set portion.

Selection from scikit-learn 1.9.1 `load_digits()`: for each target 0–9, take its first 30 rows by the original zero-based loader index, merge those indices and sort ascending. The resulting 300 rows contain 30 of each label. Labels therefore influence selection but never enter the embedding fit. The subset favors earlier observations and is neither a random nor population-representative sample. No missing observations are imputed.

[`digits-300.csv`](digits-300.csv) preserves the source's integers exactly. Columns are `source_row`, `digit`, then `pixel_0` through `pixel_63` in row-major order. Source rows are identities, not indices 0–299: for example, row 306 is a valid selected identity. SHA-256: `d93f963c4b2610eb07122a312eec3ddceac18a031477370d71e33835eced728e`.

All fits use `X = pixels / 16`. Neither identifier nor label is a numeric fit feature. This common scaling preserves Euclidean neighbor rankings; no per-pixel standardization is applied. PCA centers within its fit. Visible neighbor lists and retention R use ascending source-row IDs to resolve equal distances. Native trustworthiness T and reversed-argument continuity use scikit-learn's own sorting convention; their tie-boundary semantics can differ.

[`calculated-inputs.json`](calculated-inputs.json) contains the exact ordered source-row list and every fitted coordinate array/metric available in the lesson. All 300 coordinate rows follow the CSV order. The nine PCA/t-SNE layouts preserve the 12 September authoring arrays without rounding or replacing them. Their source versions were Python 3.12.14, NumPy 2.3.5 and scikit-learn 1.9.1. PCA uses two components and full SVD. t-SNE uses two output coordinates, perplexities 5/30/80, PCA initialization, seeds 7/19, auto learning rate, early exaggeration 12, 1,000 iterations, Barnes–Hut angle 0.5 and `n_jobs=1`. Two additional perplexity-30 layouts use random initialization and seeds 7/19. These seed pairs are separate recorded fits; equal PCA-initialized arrays are intentionally retained as an informative null result.

During implementation on 14 September, all four complete displayed programs were executed in a separate repository-local Python environment. [`runtime-versions.json`](runtime-versions.json) records the exact numerical packages, including UMAP 0.5.12, SciPy 1.18.1, Numba 0.67.0 and PyNNDescent 0.6.0. The digits comparison reproduced its saved arrays with 12-thread BLAS/OpenMP pools, matching the original host configuration. `n_jobs=1` alone does not pin those pools: a one-thread probe produced different t-SNE coordinates, which were not substituted into the saved maps. Environment, initialization and thread settings can affect an optimizer's result even with a seed. The retained arrays support exact independent audits without refitting.

[`inspect_umap.py`](inspect_umap.py) actually produced [`umap-digits.csv`](umap-digits.csv), whose four columns are source row, digit, map coordinate 1, map coordinate 2, with no header (matching NumPy's displayed export). Its settings are 15 neighbors, minimum distance 0.1, spread 1, two components, Euclidean metric, spectral initialization, random state 7, transform seed 7 and `n_jobs=1`; BLAS/OpenMP and Numba used one thread. Recorded output: UMAP 0.5.12, shape `(300, 2)`, `R10=0.7143 T10=0.9890`. This is a measured layout; no synthetic scatter points were added. All map axes have arbitrary coordinate units, and raw radii are not comparable across methods.

[`compare_transforms.py`](compare_transforms.py) used one stratified 225/75 training/validation split, random state 7. Input normalization was the fixed division by 16; reducers fitted only the training rows, then transformed validation rows. Classifier labels were used only by 5-nearest-neighbor classification. Recorded accuracies: pixels `0.9733`, PCA with 10 coordinates `0.9733`, UMAP with 10 coordinates `0.9467`. Transform left the fitted training reference coordinates unchanged. This is one validation split of the selected collection, not a final independent test or a universal ranking. Its unfavorable UMAP result is preserved.

The installed UMAP source was checked for the local calibration's excluded self column/log₂(k) target, fuzzy union, sampled vertex repulsion and use of the fitted reference during transform. The lesson's ideal single-pair loss remains an analytic explanatory model rather than a recorded UMAP optimizer trace. The exact four-point t-SNE example and its bounded offline trace have no momentum or early exaggeration.

Download and run [`inspect_digits.py`](inspect_digits.py), [`inspect_umap.py`](inspect_umap.py), [`compare_transforms.py`](compare_transforms.py) or [`tiny_tsne.py`](tiny_tsne.py) beside the CSV. Numeric arrays preserve image identity for verification. No recognition benchmark, density estimate, empirical topology certificate or runtime speed comparison is claimed by the map data.

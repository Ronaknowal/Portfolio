# Cross-domain curriculum coverage and authoring plan

Reviewed: **9 September 2026**. Scope: the 26 existing tracks other than `hardware-systems` and `computational-neuroscience`, which have independent domain plans. This is a **catalogue structure and prerequisite audit**, informed by primary curricula and documentation. The verified pre-expansion snapshot contains **1,006 topic entries across all 28 tracks (1,002 unique IDs), including 948 entries in these 26 tracks**. It is not a claim that every existing entry has received an individual technical or pedagogical review.

The implementation adds **85 topic-specific authoring blueprints** across 25 tracks and records an explicit no-addition decision for the glossary. It also supplies **51 prerequisite bridges for existing topic titles**. Existing titles remain unchanged. The detailed implementation is [cross-domain-expansion.js](../../src/learn/data/curriculum/cross-domain-expansion.js); the descriptions below summarize that source rather than replace its per-topic outcomes, sequence, visual, practice and review contracts.

These are plans for lessons, not completed educational content or built interactive labs. A complete catalogue is not the same thing as an end-to-end taught curriculum. No finite syllabus contains literally all knowledge; the intended result is a coherent foundation-to-specialist map with explicit remaining boundaries.

## What the audit found

The catalogue already contains substantial specialist breadth. Its main gaps are often **before** the named algorithms: mathematical language and proof, measurement and experimental units, meaningful data contracts, complete training and evaluation workflows, and the physical and software interfaces needed to make robot components work together. Adding more model names would not repair those transitions.

A final completeness pass converted substantial branches that were initially described only as future depth into **16 explicit catalogue plans**: four analysis/algebra/PDE topics, four flow/geometry/advanced-structure topics, two operating-system/concurrency topics, one networking topic and five nonlinear/contact/autonomous-robotics topics. A needed branch should be visible in the syllabus even when its lesson has not been written.

The current Linux lesson provides a useful authoring baseline: a path tree, stream routing, permission checks and a process-state model each answer a different question. Their mechanisms are visible instead of being left to a learner to infer from a table. Other subjects need the same reasoning, with representations fitted to their concepts, not four mandatory labs or one identical template.

## Prerequisite and path integration

`crossDomainPrerequisites` names 51 existing entry topics with critical prerequisite titles. New blueprints carry their own lists. This is intentionally selective: an unspecified old topic has **unknown or still-to-be-authored prerequisites**, not automatically none. Preserve that distinction in manifests and progress UI.

1. **Use dependency traversal, not only track order.** The current complete-curriculum order reaches DSA before mathematics and reaches some cross-domain tools after their uses. Maths proof/logic bridges must be allowed to appear before DSA correctness, and a robotics environment lesson may need MDPs before its nominal track position. Stable topological traversal should retain local order when dependencies do not constrain it.
2. **Place foundation sections before specialist catalogues, then respect each topic's dependencies.** Appending these sections at the end would leave the original beginner gaps intact. A section mixes foundation and intermediate plans when they share a conceptual family; level and prerequisite metadata control the appropriate route.
3. **Keep robotics estimation separate from control before joining them.** Frames/calibration/probability → Bayesian localization → the existing bundled PID/Kalman lesson. ODEs/actuation/kinematics → dynamics → control. Graph-SLAM builds from localization; its title does not depend on the existing broad SLAM page, preventing a circular prerequisite.
4. **Reuse frontier robotics topics as depth.** Existing `Robot Perception (LiDAR, Depth Sensing, Sensor Fusion)`, `SLAM (Simultaneous Localization and Mapping)`, `Motion Planning & Path Planning (RRT, A*, Trajectory Optimization)` and manipulation titles remain canonical. New plans make missing mechanisms explicit rather than rename or clone these entries.
5. **Make quantum prerequisites proportional.** The quantum bridge introduces necessary complex arithmetic directly; learners should not have to complete Fourier and Laplace analysis to encounter amplitudes. A link to an optional refresher is appropriate.
6. **Share numerical foundations with GPU systems.** `Floating-Point Representation & Numerical Error` is owned by the GPU plan. The distinct maths addition `Conditioning, Stability & Numerical Analysis` depends on it and focuses on problem sensitivity, residuals, forward/backward error and algorithmic stability. It is not a second IEEE-754 tutorial.
7. **Avoid hidden frameworks in conceptual prerequisites.** The mini-batch/autograd mechanism can be taught with small arrays; the named framework lesson then applies it. Requiring PyTorch before the framework-mechanics bridge would create a cycle. CUDA is not required to train the planned tiny CPU-sized language model.
8. **No automatic scope expansion from prerequisites.** A topic can supply a concise necessary bridge instead of sending a beginner through an entire field. During full authoring, prerequisites should be observable abilities with direct links or refreshers, not a long intimidating reading list.
9. **Give advanced applications their real foundations.** Measure theory and RKHS point to real-analysis convergence; geometric deep learning points to the symmetry bridge; PINNs and neural operators point to PDE formulation; humanoid whole-body control points to hybrid legged mechanics. These new specialist entries remain optional for unrelated beginner routes.
10. **Distinguish networking layers and CPU concurrency from GPU topics.** Packets/transport/sockets precede HTTP/service semantics. CPU process address spaces and shared-thread invariants are not replaced by a GPU unified-memory or warp-synchronization lesson. Reuse conceptual ideas with explicit execution-model differences.

The selected override graph plus new cross-domain plans was checked for missing titles and cycles. A combined check including the GPU and neural additions and the GPU prerequisite overrides also passed at this snapshot, with no duplicate new cross-domain titles against those plans. Root catalogue and path integration is implemented and its combined structural checks pass. Any later changes to edges or titles must rerun those checks; see [the integration verification record](../../CURRICULUM-EXPANSION-VERIFICATION.md).

## Authoring method: retain the established teaching direction

Use [LESSON-TEACHING-STANDARD.md](../../LESSON-TEACHING-STANDARD.md) as the full reusable brief. For each selected topic:

1. **Inspect its actual existing implementation.** Record what is worth preserving, which outcomes are already supported, and which explanation, visual or practice step is weak. A catalogue title is not evidence of coverage.
2. **Start from a concrete question.** Explain entities and purpose in ordinary language, then introduce the terms and notation needed for the next step. State units, dimensions, operating context and data provenance where they matter.
3. **Use one continuing example per coherent mechanism.** Show inputs, intermediate states, result and interpretation. A changed-context example establishes transfer; a complete small workflow connects the parts.
4. **Assign representations to conceptual hurdles.** Proofs need invariant traces; probabilities need outcome/mass representations; gradients need update-state traces; masks need token grids; robotics needs frames, timelines, forces and beliefs. Exact tables complement these relationships. One lab per page is not a rule. Use multiple focused labs or static diagrams wherever they teach distinct mechanisms.
5. **Give the learner a prediction before the reveal.** Each blueprint names a visual question and interaction. The finished lesson should provide controls with meaningful default states, a reset or replay, accessible labels, explanatory feedback and explicit simulation limits.
6. **Develop sufficient depth for the scoped outcome.** Move from intuition through mechanism, formal detail, worked example, practical workflow, failure cases, independent practice and optional deeper branches. “Beginner-friendly” does not justify incorrect simplifications; “advanced” does not justify unexplained notation.
7. **Practise with decreasing support.** Offer hints before full solutions, diagnosis of tempting wrong approaches, and an independent transfer task with explicit success criteria. Avoid quizzes that only test the latest noun definition.
8. **Validate independently.** Execute displayed code and numerical examples against a reference, check prerequisite reachability, and review visuals on desktop/mobile with keyboard use. Version-sensitive libraries, model claims and standards receive a fresh primary-source review at implementation time.
9. **Report separate statuses.** Planning, implementation, numerical/behaviour verification, browser/visual review and user review are different states. A blueprint is not a ready lesson, and a build pass is not proof of learning quality.

The new fields are intentionally topic-specific: outcomes are behaviours, sequence stages name mechanisms, visual questions invite causal inspection, and practice criteria define observable evidence. They are starting contracts; a finished lesson may need more than the one visual described in its compact blueprint.

## Investigation 1 — when does a gradient become an update?

Placement: end of §3. Question: when do extra backward calls change only the gradient buffer, and when does a changed boundary change the parameters? Show weight after the first backward call and after the selected full policy immediately, alongside the correct-policy result. Step the trace to follow the operation causing each change.

Entity controls: edit each row's x/y in [−5,5] in .25 increments; add/remove rows up to eight, minimum one; change whether a boundary follows each nonfinal row; edit learning rate in [0,.2] with .01 steps. Row IDs stay stable on regrouping. Select policy `one update after all chunks`, `clear before every chunk`, or `step and clear after every chunk`. The last is explicitly a changed algorithm; it both updates parameters and resets grads after each chunk. Its later gradients are recomputed at the new weight. Do not implement a hybrid that accidentally carries a stale gradient after the early step. Optimizer selection and all entities form part of live recomputation.

Computation: for each forward at current w, row loss=.5(wx−y)^2, raw derivative=(wx−y)x. Backward contribution is sum(raw derivatives)/N, where N is all rows in this effective group even in the fault policies. One-step policy adds all contributions, then v=μv+g (μ=0 for SGD) and w←w−ηv. Clear-per-chunk removes preceding contributions but leaves parameter/optimizer unchanged until the final step. Step-per-chunk applies v/w after every chunk, clears its gradient and reevaluates subsequent chunks. Optimizer step count visibly differs; the independent update counter is not mislabeled epoch.

State views: editable row table with predictions/errors/individual gradients populated only in the current live view; highlighted current code operation; lane for parameter, current gradient slot, optimizer buffer or `SGD: no memory`, examples processed, backward-call count, optimizer-step count.

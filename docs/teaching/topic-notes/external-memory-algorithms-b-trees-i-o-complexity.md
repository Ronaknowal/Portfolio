## 2026-09-10 — A shared root is not a crash-safe committed root

- Status: adapted on 10 September 2026.
- Origin: [Persistent Data Structures design](../PERSISTENT-DATA-STRUCTURES-LESSON-DESIGN.md), sections 4 and 8 of its authored lesson.
- Verified destination: scoped topic inventory confirms `external-memory-algorithms-b-trees-i-o-complexity`, the next DSA module topic, with B-tree fanout/block transfer and SQL prerequisites. No catalogue changes were made.
- Current coverage: the origin implements immutable in-memory branching roots and counts reachable objects. It explicitly distinguishes data-structure persistence from durable storage. The receiving brief explains block transfers but does not yet contain a published body or a commit-protocol walkthrough.
- Proposed treatment: while teaching page-oriented updates, contrast the RAM path-copy allocation count with copying/writing blocks. Explain that saving a root reference before the pages it reaches are safely written can leave an invalid recovered tree. Use a small staged page/root publication diagram and crash points, with the actual chosen storage protocol's ordering and atomicity assumptions. This can be a bounded deeper connection; do not turn the I/O lesson into an entire database recovery course.
- Why here: block layout, write ordering and durability are the new concepts; they should not be smuggled into the predecessor lesson's immutable-node proof. Coordinate with the existing SQL/transaction treatment and deeper database owners if extending recovery or MVCC.
- Practice: identify which root is recoverable after each interrupted stage and account for transferred pages separately from RAM node allocations. Never infer real fsync or hardware behavior from a simulated counter.
- Sources: [SQLite atomic commit](https://www.sqlite.org/atomiccommit.html), introduction/hardware assumptions and rollback-journal staging inspected. It documents a rollback-mode design, not the same method as copy-on-write root publication; use it to compare guarantees and assumptions, not as a purported implementation of our proposed diagram. Review the primary documentation for whatever actual page-copy protocol is chosen.
- Resolution: implemented as the bounded abstract shadow-page protocol in section 6, “Publish a root that can survive.” The single-writer, immutable-old-page, durable-write and atomic durable-root assumptions are explicit. The learner can interrupt every stage and compare correct ordering against premature root publication. Both complete new-page reachability and acknowledgement uncertainty are explained. SQLite is a contrasting rollback-journal protocol, not claimed as this simulation's implementation.
- Implementation: [lesson design](../EXTERNAL-MEMORY-LESSON-DESIGN.md), `ShadowCommitLab` in `src/learn/components/lesson-labs/ExternalMemoryLabs.jsx`, `shadowCommitTrace` in `src/learn/data/external-memory-models.js`, the complete native `crashRoots` example, and local exercise 6 plus the integrated exercise 7.
- Verification: `scripts/verify-external-memory.py` independently checks durable graph reachability for all twelve safe/broken states and verifies actual native stdout. Final browser/freeze evidence belongs in [External-Memory verification](../EXTERNAL-MEMORY-VERIFICATION.md); publication is not equivalent to completed author review or user acceptance.

# Static and moving range summaries: assess monotone-deque coverage

## 2026-09-10 — Match a range structure to the operation and dominance relation

- Status: implemented in the destination lesson, section 7, after scoped assessment on 10 September 2026.
- Origin: Binary Search, Sorting & Two-Pointer Patterns, currently implemented under the active DSA rollout. See [its design record](../ORDERED-PATTERNS-LESSON-DESIGN.md).
- Proposed destination: **Segment Trees, Fenwick Trees & Range Queries** (`segment-trees-fenwick-trees-range-queries`). This existing topic is a reasonable place to compare static prefixes, moving-window structures and dynamic range trees. It is a proposal to reassess, not an instruction to force every deque mechanism into a tree lesson. Choose a better existing owner if its prerequisites/learning flow fit better, then reroute the note explicitly.
- Current coverage: the origin teaches fixed-width signed sums, shortest-at-least nonnegative windows, uniqueness windows, prefix/suffix summaries and signed exact-sum frequency counting, including why different validity rules need different state. It does **not** teach monotone-deque optimization for signed shortest-at-least windows or sliding extrema. A narrow search of DSA catalogue/brief titles found no explicit monotonic-stack/deque owner; this is not a full-site content audit. Earlier queues establish FIFO mechanics, not these dominance proofs.
- Concrete counterexample: `[1, -1, 5]`, target `5`. A positive-only grow/shrink algorithm reaches sum 5 over all three entries, removes 1, observes sum 4 and stops shrinking. It misses `[5]` because removing the negative value would increase the sum. Sorting values would alter the original contiguous-range task.
- Learning benefit: distinguish an invertible summary (sum), an operation with no simple prefix cancellation (minimum/maximum), a moving boundary and arbitrary point/range updates. Explain when a deque, Fenwick tree, segment tree or simpler prefix map is actually warranted, rather than mapping all “range” questions to one memorized structure.
- Proposed depth and representation: derive a monotone deque using candidates and dominance, not merely its name. For a maximum window, a newer value at least as large can dominate an older value because it survives at least as long and is at least as good; expiration and domination remove entries for different reasons. Use an index timeline beside a candidate deque with explicit removal reasons. For signed shortest-at-least, prefix totals are not ordered by time; maintain candidate prefix indices with increasing totals, justify deleting a back candidate whose prefix is no smaller than a newer prefix, and justify recording/removing front candidates once the target is met. A newer start with no greater prefix gives no smaller future range sum and a shorter future interval. The algorithm requires a complete invariant/termination argument and careful lookup/update order.
- Prerequisites: prefix boundaries, signed cancellation, queue/deque operations, half-open ranges, amortized one-entry/one-removal reasoning. Teach each required bridge or link verified prior coverage. Do not assign an unexplained difficult external problem as the explanation.
- Independent practice: compare against brute-force ranges on negative values, zeros, repeated prefixes, expired candidates, all-equal readings, empty/no-answer cases and ties. Trace both expiry and dominance separately. Consider preserving an earliest versus latest argmax identity; changing tie deletion affects that contract even when the maximum value stays correct. Count total deque pushes/pops under a declared constant-cost model and test actual native implementations.
- Sources/uncertainty: origin's elementary identities and counterexample were independently checked. Specialized deque claims above are a proposal requiring primary/authoritative source research and native/model/browser verification by the destination author. No specialized runtime or universal interview-coverage guarantee is claimed here.
- Resolution: included as two distinct range-query mechanisms. The fixed maximum investigation exposes expiry versus value domination and newest-tie identities; the signed shortest investigation plots exact prefix totals and separately proves valid-front retirement and dominated-back retirement. Complete Python programs, exhaustive finite contiguous-range oracles, operation-count checks and changed-objective exercises are present. Official LeetCode 239 and 862 are annotated transfers, not the explanation. See [lesson source](../../../src/learn/data/topics/segment-trees-fenwick-trees-range-queries.jsx), [design](../RANGE-QUERIES-LESSON-DESIGN.md) and [verification](../RANGE-QUERIES-VERIFICATION.md). ## 2026-09-10 — Range maxima can accelerate a proved DP transition

- Status: implemented in section 8 after deriving the required range-maximum and compression mechanisms.
- Origin: `dynamic-programming-states-transitions-optimization`, [design](../DYNAMIC-PROGRAMMING-LESSON-DESIGN.md).
- Existing coverage: DP derives LIS ending-at-index in quadratic time and a minimum-tail dominance optimization for unweighted length. It explicitly warns that the tails array is not a witness and that weighted/counting objectives require new summaries. The next range-query topic is the plausible owner for replacing a scan of earlier states by a range aggregate.
- Proposed treatment: for strictly increasing values, process positions in input order, coordinate-compress value ranks, query the maximum DP score at ranks strictly smaller than the current value, then update its rank. A weighted variant gives the range-maximum data structure a learning job that a minimum-tail length summary does not automatically solve. Define empty-selection/negative-score and duplicate/tie policies before initializing the identity. State whether point updates replace or take max.
- Why here: the range structure, coordinate compression and online query/update contract need teaching before optimizing the recurrence; the preceding DP lesson supplies state sufficiency and the exhaustive predecessor scan. Do not silently reorder the curriculum or add an unexplained Fenwick implementation to DP.
- Suggested verification: compare against the direct O(n²) recurrence and exhaustive subsequences on short signed-weight inputs, duplicates and negative-only inputs. Query before updating, use an exclusive rank boundary for strict increase, and validate any witness identity or counting extension separately.
- Primary source inspected: [CMU 15-451 spring 2025 DP slides](https://www.cs.cmu.edu/~15451-s25/slides/lecture11.pdf), slides 4–5 describe LIS with a segment-tree route. Some formulas are left blank in the unannotated slides; they do not by themselves verify a complete implementation. Receiving author must derive, research and independently check the chosen weighted/counting extension.
- Resolution: derived weighted strictly increasing subsequences with the empty selection allowed. Original position order is retained; an exclusive smaller-rank query happens before max-updating the rank. Signed weights, duplicate values, deterministic endpoint ties, all-negative/empty inputs and backward parent reconstruction are explicit. The computed walkthrough retains actual occurrence identities and gives score 25 with witness indices [1,3,4]. Complete native and bounded model implementations were independently checked against exhaustive subsequences (800 fixtures each), including witness score/order/strictness. Counting-LIS extensions remain outside this implemented weighted-score contract. See [design](../RANGE-QUERIES-LESSON-DESIGN.md) and [verification](../RANGE-QUERIES-VERIFICATION.md).

# Schedule clocks, optimizer conventions and cumulative decay

## 2026-09-10 — Connect a schedule to actual state transitions

- Status: resolved — included and verified in the Learning Rate Schedules rewrite on 10 September 2026.
- Origin: `gradient-descent-variants-sgd-adam-adagrad-rmsprop-lamb-lars`, [individual design](../GRADIENT-DESCENT-VARIANTS-DESIGN.md). Its complete rewrite is in progress, not yet verified.
- Proposed destination: `learning-rate-schedules-cosine-warmup-onecyclelr`. The complete current old body was read. It gives an update-based warmup/cosine example but broadly claims differing schedules make optimizer comparison unfair, and that schedules usually step per optimizer update. The replacement should define the clock rather than treat either phrase as a universal rule.
- Why this owner: the variants lesson will teach the parameter/moment/update-counter transition, an in-memory optimizer/RNG resume example and unequal-microbatch mean weighting. The next topic is the natural home for **schedule event semantics**, endpoint choices, plateau metrics, warm restarts and scheduler checkpoint state.
- Concrete connections: AdamW direct shrinkage with zero adaptive displacement yields `theta_T = theta_0 * product_t(1 - eta_t*lambda)`, so decoupled decay still depends on the rate path. This identity assumes actual optimizer updates on that parameter, no skipped/missing-gradient update and the defined coefficient convention. Restoring weights without moments/update count changes Adam; restoring those without the scheduler clock still changes the next rate. The origin uses full numerical state/RNG cloning, not a claim that it implements production loader/checkpoint persistence.
- Momentum conventions: a velocity that stores `eta_t*g_t` and one that stores `g_t` can match under constant eta with a rescaled state, but cannot be casually identified after eta changes. LARS example explicitly stores the scaled contribution inside velocity; the basic momentum example stores the gradient and applies eta afterward. The schedule lesson should either preserve one convention or explain/test the transformation, not claim that changing a displayed rate always rescales all past contributions identically.
- Endpoints in the old code: a ten-update, two-warmup-step cosine example repeats its maximum at indices 1 and 2 and ends above its supplied minimum because the decay progress does not reach 1 at index 9. That can be an intentional discrete convention, but needs an explicit before/after-step timeline and endpoint contract. The origin does not prescribe a replacement formula.
- Comparison: identical objective/data/init and documented compute/data exposure matter; blindly imposing the same learning rate or schedule on structurally different optimizers can handicap one method. Distinguish an isolation experiment from independently tuned optimizer-plus-schedule configurations. Do not promise universal training/generalization rankings from one toy run.
- Sources/evidence: exact product and momentum observations are algebraic consequences of the origin's stated update equations; no external empirical claim. PyTorch2.14 optimizer docs were inspected for momentum/AdamW conventions; scheduler API contracts must be independently reviewed by the receiving author. Parent coordination explicitly requests that scheduler frequency not be assumed universally per batch.

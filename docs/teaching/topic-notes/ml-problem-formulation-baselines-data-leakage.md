## 2026-09-10 — An older event can still contain information from the future

- Status: open
- Origin: `pandas-data-wrangling-joins-grouping`; [topics 6–8 design](../next-three-reimplementation.md), optional backward-calibration example.
- Destination and ownership rationale: this topic introduces prediction time and legitimate feature availability. It is the primary home for deciding whether a historical join is scientifically valid. Pandas owns the mechanics; the later Time-Series Validation and Data Contracts lessons can extend the same contract rather than independently redefine it.
- Idea and learning benefit: learners should distinguish when an event happened, when its value became available, and when a prediction had to be made. A backward match on event time alone can still select a late correction that the deployed model could not have seen.
- Existing coverage: the bespoke plan in `src/learn/data/curriculum/cross-domain-expansion.js`, “ML Problem Formulation, Baselines & Data Leakage,” already includes a data-availability timeline and moving arrivals across the prediction boundary. The concrete connection to the Pandas calibration fixture and late revisions is not specified there. This is a refinement of that planned activity, not a request for a duplicate lab. No destination lesson was rewritten or audited in this increment.
- Proposed treatment: after defining prediction time and before auditing a suspicious score, adapt the existing timeline to show both event and available-at markers. Introduce a late correction as a second case. Keep deployment/availability semantics in the core explanation; a library-specific implementation may be optional. The existing topic title already fits.
- Explanation/example: reuse the invented calibration scenario. A reading needs a prediction at time 5. A calibration has event time 4 but arrives at time 8. It is recent enough for the original backward match yet unavailable at time 5. Ask which earlier available calibration, if any, should be used. Move arrival time from 8 to 4 without changing event time; require a reasoned prediction before revealing the admissible match. An optional extension gives a later revision to the same event and asks which version was visible at the cutoff.
- Prerequisites and boundaries: teach target, feature and prediction deadline first. Do not equate a database creation timestamp with actual serving availability unless that contract is established. A matching tolerance limits age; it does not by itself encode availability, train/test separation or preprocessing provenance. The Pandas lesson states a simplified immediate-availability assumption and links here.
- Evidence: [Pandas merge_asof API](https://pandas.pydata.org/docs/reference/api/pandas.merge_asof.html), backward key matching and tolerance; [Feast point-in-time joins](https://docs.feast.dev/getting-started/concepts/point-in-time-joins), especially “Retrieving features as of the event time,” reviewed 10 September 2026. Feast explicitly distinguishes event-time matching and created-time filtering, including late backfills and support limitations. This is evidence for the distinction, not a claim that all feature stores behave alike. The calibration scenario is an invented teaching example. The origin's simpler matching arithmetic was run under Pandas 3.0.1; the proposed late-arrival exercise and Feast API have not been implemented or runtime-tested here.

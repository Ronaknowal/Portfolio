# Handoffs, cross-topic continuity and cleanup

Use during a substantive topic/phase handoff, when an idea belongs to another topic, or for an explicit scoped cleanup request. These steps maintain the existing records; they do not create a third delivery phase or another review campaign. Read the [repository adapter](portfolio-adapter.md) for actual paths and schemas.

## Carry learning decisions between topics

For a new connection, inspect the actual existing coverage and select its best teaching owner. Save the origin, receiving stable ID, reason for that ownership, learner benefit, prerequisite skills, proposed placement/depth, useful example or visual, sources and remaining uncertainty. Explain the local bridge in the current lesson where helpful; a saved future task cannot replace a promised core explanation. If no owner exists, use the repository's unresolved routing inbox rather than inventing a topic ID.

Record continuity when it matters: which earlier result, notation, dataset, code contract or diagram this topic reuses; the new problem or limitation it addresses; and what later topic can build on the result. Link the exact section/program and summarize the contract needed here. Keep a consistent example when it helps, and explain a switch of assumptions, units or representation. Do not force one story or dataset across unrelated subjects. A next-study link must respect the catalogue sequence; an interesting later application is a separate optional connection.

Read relevant destination notes before writing, and reassess discoveries that arise during writing or verification. Investigate rather than paste an earlier agent's proposal. Resolve each relevant note as included/adapted, rerouted, deferred with a revisit condition, or rejected with a reason. Use the repository's existing status vocabulary. Link the actual section and supporting checks when implemented. A content-only manuscript can record a prepared disposition while implementation remains open; reading a note or writing a plan does not mean the idea was implemented.

## Keep the ledger and resumable record useful

At a substantive transition, record the selected topic/revision/mode, content and implementation states, actual source identities, design/source links, checks performed, unresolved findings and one precise next action. Use the central ledger and its existing linked record. Preserve previous revisions and distinguish user acceptance from technical completion. Do not invent dates, hashes, successful executions or independent review.

Close completed actions in the active handoff rather than appending them as perpetual TODOs. Retain the result and its evidence link in the topic record. Active summaries should foreground remaining work; resolved decisions remain retrievable for provenance, reuse and avoiding duplicate work. Correct a stale summary from the actual ledger/source, not by promoting an unfinished phase to make the summary agree.

Before an interruption, prioritize saving the actual partial work and next action. Do not destroy temporary inputs still needed to resume. For another agent, provide the exact mode/topic, current source/packet, unresolved question and relevant reference paths. It still reads the complete affected lesson; a short handoff is not a replacement for substantive review.

## Routine cleanup is part of delivery

At each topic or phase boundary, inspect only the working material created or consumed by that scoped task. Use the same process for an explicit **cleanup** request. Do not run a whole-repository scratch audit at every start or exit. An elapsed date, ignored path or completed topic alone is not evidence that a file is disposable.

Respect an explicit read-only request: report suggested record/cleanup changes instead of editing the user's artifacts. Routine housekeeping may remove only disposable temporary files the agent itself created for that review, when allowed. Cleanup instructions do not expand a review into permission to modify its subject.

| Material | Default action |
| --- | --- |
| Failed downloads, temporary patch helpers, redundant logs, duplicate/superseded screenshots and installed duplicate working drafts | Remove once their role is finished, useful results are recorded and ownership/dependency checks establish they are disposable. |
| Pending manuscripts, explained programs, visual specs, necessary datasets and unresolved findings | Retain until the consuming phase is actually complete. “Research and write complete” is not permission to delete the packet. |
| A prepared packet consumed by successful implementation | Retire only redundant copies, after validating equivalent retained content/specifications and checking both current and historical consumers. Follow the ledger contract before changing authoritative paths. Keep the original if a receipt/verifier still needs it or equivalence is uncertain. |
| Open/deferred cross-topic notes | Retain their rationale, evidence and next condition. Completing the originating lesson does not resolve the destination's work. |
| Implemented/adapted/rejected/rerouted notes | Retain a concise disposition and exact destination/evidence links; remove redundant active reminders, not the decision history. Preserve useful substantive reasoning and any source-bound record. |
| Runtime code/assets, reusable checks, shared environments, required inputs, exact baselines and final review evidence | Retain. “Used already” is often the reason these are still needed. |
| Historical handoffs and passed reviews | Keep required provenance accessible; stop loading them by default. Do not rewrite a frozen result to describe a new execution. |

Before deleting, check known runtime/dynamic references, source-hash bindings, evidence attachments, script inputs, active workers/processes and user-authored changes. A filename search alone is insufficient. Remove only verified disposable material within the authorized scope. Leave uncertain/shared work and briefly record why; do not let uncertainty about one file prevent independent safe housekeeping.

Use platform-safe literal-path operations. On Windows resolve each target, verify it is within the explicitly intended workspace directory, and reject unexpected links/reparse points/path escapes. Never wipe a broad scratch tree or dependency environment. Do not delete referenced originals and silently refresh hashes to make the ledger green. Archive only material with a real recovery purpose; moving all junk to an archive does not solve accumulation.

Record cleanup once in the existing scoped record: actual removals and reasons, retained counterpart when relevant, protected inputs and any unresolved ownership. Check affected links/paths, remaining inputs and source/ledger identity. A documentation-only or disposable-file cleanup does not need a new scientific execution or website build. If deletion changes runtime dependencies, it is an implementation change requiring its proper checks, not ordinary cleanup. Remove any disposable inventory created for the cleanup itself.

## Reduce future context without losing knowledge

Keep standards in the skill, current state in the ledger/handoff, and topic-specific claims/decisions in their semantic owners. After a conclusion is saved, reference its durable location instead of copying full transcripts, tool output or entire lessons into every handoff. Promote a reusable teaching lesson into the existing canonical guidance only when it improves future decisions; do not add a universal rule for every isolated defect.

Load the current record and relevant unresolved notes first; consult resolved evidence only for a specific dependency, question or changed source. After compaction or a new session, recover missing instructions and exact artifacts instead of replaying old campaigns. Keep full content available for genuine teaching review. Context efficiency never justifies deleting needed knowledge or omitting verification.

This skill instructs the active agent to do housekeeping at delivery boundaries. It does not schedule background work, delete prior chat messages, or guarantee that loaded conversation text is removed. Keeping future retrieval focused and the saved state current is the supported approach. A standalone cleanup mode is useful for older accumulation or a user-selected scope, not a mandatory extra step after every topic.
